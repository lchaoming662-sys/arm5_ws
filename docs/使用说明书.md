# O5-2 五自由度桌面机械臂 · 使用说明书

> 本工程是 O5-2 机械臂的 ROS 2 描述 + 控制 + 仿真 + 抓取演示工程，
> 结构参照 `akabot`（参考实现）与《11 从零手敲代码实战》（说明手册）重建。
>
> 原始素材是 WSL 导出的 `~/arm_description`（单包、Gazebo Classic），
> 本工程是它的**重构版**：拆成 3 个包、迁到 Gazebo Fortress、清掉全部冗余配置。
> `~/arm_description` 与 `~/ros2_arm` **未被修改**，可随时对照。

---

## 一、快速开始

先 source 环境（每个新终端都要）：

```bash
source /opt/ros/humble/setup.bash
source ~/arm5_ws/install/setup.bash
```

**一条命令起全链路**（仿真 + 控制器 + MoveIt + RViz，推荐）：

```bash
ros2 launch arm_bringup bringup.launch.py
```

**想分步来**（调试、或只想跑其中一段）：

```bash
ros2 launch arm_description description_launch.py   # ① 只看模型（RViz + 关节滑块）
ros2 launch arm_gazebo gz_launch.py                 # ② 仿真（Fortress，含控制器）
ros2 launch arm_moveit_config demo.launch.py        # ③ MoveIt 规划（需 ② 在跑）
python3 ~/arm5_ws/tools/pick_demo_moveit.py         # ④ MoveIt 抓取演示（需 ②③ 在跑）
python3 ~/arm5_ws/tools/pick_demo.py                # ⑤ 旧版抓取演示（写死关节角，需 ② 在跑）
```

> ② 与 ③ **有先后**：③ 里的 `move_group` 要等控制器 active。一条命令版已经把这件事
> 用门闩节点串好了（见 5.4），分步版得自己看日志确认②好了再起③。

**注意**：本机还装着旧的 `~/arm_ws`（Gazebo Classic 版 `arm_description`）。
**不要和 `~/arm5_ws` 同时 source**——两个工作区有同名包，`package://arm_description/meshes/...`
会解析到谁不确定。新开终端只 source 上面两行。

## 二、环境要求

| 项 | 要求 | 本机实测 |
|---|---|---|
| ROS 2 | Humble | `/opt/ros/humble` |
| 仿真器 | **Gazebo Fortress**（ign gazebo 6） | 6.18.0 |
| 桥接 | `ros_gz_sim` / `ros_gz_bridge` / `ros_gz_image` | 齐全 |
| 硬件接口 | `gz_ros2_control` | 0.7.x |
| 控制器 | `joint_trajectory_controller` / `gripper_controllers` / `joint_state_broadcaster` | 已装 |

`ign_ros2_control/IgnitionSystem` 的兼容别名，所以两种插件名都能用）。

**为什么拆 3 个包**（照 akabot / 手册的职责划分）：

| 包 | 只负责 | 不负责 |
|---|---|---|
| `arm_description` | 模型是什么样 | 怎么控制、在哪跑 |
| `arm_bringup` | 控制器怎么配 + **总装入口**（把下面两个包串起来） | 模型、世界 |
| `arm_gazebo` | 在哪跑（世界 / 桥 / 启动） | 模型、控制器参数 |

好处：换仿真器只动 `arm_gazebo`；上真机只动 `arm_bringup`；模型两处共用。

## 三·补、命名约定（对齐参考工程 akabot）

模型里不用编号名，连杆与关节都用**语义名**（这条是照 akabot 改的）：

| 连杆 | 关节 | 是什么 |
|---|---|---|
| `base_plate` | `base_plate_joint`（fixed） | 底板 |
| `top_plate` | `top_plate_joint` | **底座回转**（轴 `0 1 0`，因整体 +90° about X 等效世界 Z） |
| `lower_arm` | `lower_arm_joint` | 肩部俯仰（轴 `1 0 0`） |
| `upper_arm` | `upper_arm_joint` | 肘部（轴 `-1 0 0`，与上者反向） |
| `wrist` | `wrist_joint` | 腕俯仰（轴 `1 0 0`） |
| `claw_base` | `claw_base_joint` | **腕回转**（轴 `0 0 -1`） |
| `right_claw` | `right_claw_joint` | **主动指**（控制器只驱它，限位 `[-0.90, 0]`） |
| `left_claw` | `left_claw_joint` | **从动指**（`<mimic>` 主动指 ×(-1)，限位 `[0, +0.90]`） |

另外三个不参与驱动的坐标系：`world`（世界锚定）、`base_link`（空壳根节点）、
`tcp`（两指夹持面中点，规划/抓取的目标点）。

**几处与 akabot 的有意差异**（都是权衡后的选择，不是漏改）：

| 项 | akabot | 本工程 | 为什么 |
|---|---|---|---|
| `world → base_link` 的固定关节 | `fixed` | `world_base_link_joint` | `fixed` 在模型里太容易和"固定"语义混淆 |
| 惯量 | `box_inertia` / `cylinder_inertia`（几何近似） | `tensor_inertia`（CAD 精确张量） | 本工程有 SolidWorks 四面体积分数据，换成包围盒近似是**信息损失**。两种宏都在 `inertial_macros.xacro` 里，将来加没有 CAD 数据的连杆时可以直接用前者 |
| 网格单位 | 毫米（`scale="0.0001"`） | **米**（无 scale） | 原始 STL 就是米制 |
| 网格文件名 | 按连杆命名 | 按连杆命名 | 已对齐（`top_plate.stl` / `wrist.stl` …） |
| 总装文件前缀 | `akabot_*` | `arm_*` | 机器人名是 `o5_2_arm`，文件前缀用 `arm_` 更短且无歧义 |

**四个总装文件的分工**（一图记牢，只差"谁提供 ros2_control 的硬件接口"）：

```
arm_core.xacro        纯模型
   ├─ + 相机          → arm.urdf.xacro        显示（RViz）
   ├─ + ros2_control(仿真插件) + Gazebo 物理 → arm_gz.urdf.xacro   仿真
   └─ + ros2_control(真机插件)               → real_arm.urdf.xacro 真机（待接）
```

改模型时**只动 `arm_core.xacro`**；换硬件只动对应的总装文件 ——
这就是拆开的收益。

## 四、接口清单

### 4.1 关节（`arm_core.xacro`）

| 关节 | 类型 | 限位 | 说明 |
|---|---|---|---|
| `top_plate_joint` | revolute | [−1.5708, 1.5708] rad | 底座回转（世界 Z 轴） |
| `lower_arm_joint` | revolute | [−1.5708, 1.5708] | 肩（绕世界 X） |
| `upper_arm_joint` | revolute | [−1.5708, 1.5708] | 肘（与 lower_arm_joint 反向） |
| `wrist_joint` | revolute | [−1.5708, 1.5708] | 腕俯仰 |
| `claw_base_joint` | revolute | [−1.5708, 1.5708] | 腕滚转 |
| `right_claw_joint` | revolute | **[−0.90, 0]** | **主动指**，绕 Y 轴 |
| `left_claw_joint` | revolute | **[0, +0.90]** | **从动指，`<mimic>` 主动指 ×(−1)** |

另有 3 个固定关节：`world_base_joint`（world→base_link，把基座钉在世界原点）、
`base_mount`（base_link→base_plate，`rpy=(π/2,0,0)`，把 CAD 的 Y-up 转成 Z-up）、
`wrist_cam_mount_joint` / `wrist_cam_optical_joint`（相机）。

### 4.2 夹爪角度语义（重要）

```
 0.00 = 竖直张开位，两指夹持面间距 29.28 mm
 负方向 = 闭合。约 −0.15 rad 时两指面正好夹住 25 mm 方块
 −0.90 = 限位（再转到 −0.93 两指面才刚好接触）
```

注意：**闭合是往负值走**，正值会被限位顶住。

### 4.3 控制器（`arm_bringup/config/arm_controllers.yaml`）

| 控制器 | 类型 | 说明 |
|---|---|---|
| `joint_state_broadcaster` | JointStateBroadcaster | 从物理引擎读真实状态发 `/joint_states` |
| `arm_controller` | JointTrajectoryController | 5 关节臂 |
| `gripper_controller` | GripperActionController | **单关节**，只控 `right_claw_joint` |

### 4.4 运行时接口

```bash
ros2 action list
#   /arm_controller/follow_joint_trajectory
#   /gripper_controller/gripper_cmd

ros2 topic list | grep -E 'joint_states|camera'
#   /joint_states            （100 Hz，随 RTF 缩放）
#   /wrist_cam/image         （30 Hz，经 image_bridge）
#   /wrist_cam/camera_info   （经 parameter_bridge）
#   /clock
```

`ros2 control list_hardware_interfaces` 里 `left_claw_joint_mimic/position [unclaimed]`
是**正常的**——它由 mimic 关系驱动，不该被控制器占用。

### 4.5 MoveIt 接口（`arm_moveit_config`）

| 项 | 值 |
|---|---|
| 规划组 `arm` | 链路 `base_link → tcp`，即 top_plate_joint..claw_base_joint + 固定的 `tcp_joint` |
| 规划组 `gripper` | 只有 `right_claw_joint`（从动指由 URDF mimic 跟随，不进组） |
| 预设姿态 `arm` | `home`（全零）、`grasp_ready`（与 `pick_demo.py` 的 PREGRASP 同值） |
| 预设姿态 `gripper` | `open`(0)、`close`(−0.35) |
| IK | `kdl_kinematics_plugin/KDLKinematicsPlugin` + **`position_only_ik: true`** |
| 默认规划器 | `ompl` / `RRTConnect` |

运行时接口：

```bash
ros2 service list | grep -E 'compute_ik|apply_planning_scene'
#   /compute_ik                求逆解（验证 position_only_ik）
#   /apply_planning_scene      规划场景增删（放障碍物用）

ros2 action list | grep move_action
#   /move_action               规划 + 执行的总入口（moveit_msgs/action/MoveGroup）
```

**关于 `tcp` 坐标系**：模型的末端默认是腕关节 `claw_base`，而它离真正的抓取点
（两指夹持面中点）有 **95.925 mm**。所以 `arm_core.xacro` 里加了一个固定在 claw_base 上的
`tcp` 空 link，让规划组以它收尾。零位时 TCP 各轴相对世界系：
`+Z` 手指伸出方向、`+X` 两指开合轴、`+Y` 正交（朝下）。

## 五、常用操作

### 5.1 编译

```bash
cd ~/arm5_ws
colcon build --symlink-install
source install/setup.bash
```

`--symlink-install` 让 `install/` 指向源码，所以改 `.xacro` / `.yaml` / `.py` / `.sdf`
**立刻生效不用重编**；只有改 `package.xml` / `CMakeLists.txt` 或**新增文件**才需要重编。

> PATH 里若 Python 3.13 排在前面，ROS 工具会挂，必须用干净环境：
> ```bash
> env -i HOME=$HOME PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
>   bash -c "source /opt/ros/humble/setup.bash && cd ~/arm5_ws && colcon build --symlink-install"
> ```

### 5.2 只看模型（RViz）

```bash
ros2 launch arm_description description_launch.py                 # 关节滑块可手动摆
ros2 launch arm_description description_launch.py use_gui:=false  # 全零位
```

### 5.3 仿真

```bash
ros2 launch arm_gazebo gz_launch.py
```

启动链（`gz_launch.py` 里的顺序，缺一环都不行）：

```
① SetEnvironmentVariable  告诉 gz 去哪找 package:// 网格（不做则网格全丢，见踩坑 3）
② robot_state_publisher   展开 xacro → /robot_description + TF
③ Gazebo Fortress         -r 立即运行（不加会是暂停态，见踩坑 2）
④ parameter_bridge        clock / camera_info
⑤ image_bridge            相机图片
⑥ ros_gz_sim create       从话题把机器人生成进世界
⑦ spawner ×3              依次激活 jsb → arm_controller + gripper_controller
```

### 5.4 一条命令拉起全链路（bringup）

```bash
ros2 launch arm_bringup bringup.launch.py
```

等价于把 5.3 和 5.7 那两条命令塞进同一个 launch，**并且保证先后**：
仿真起来 → 三个控制器 active → 才起 `move_group` 与 RViz。

| 参数 | 默认 | 说明 |
|---|---|---|
| `gui` | `true` | `false` = Gazebo 只跑 server 不开界面，快 |
| `camera` | `true` | `false` = 不加载腕部相机（含图片桥） |
| `world` | `arm_world.sdf` | 换世界文件 |
| `use_moveit` | `true` | `false` = 只要仿真 + 控制器 |
| `use_rviz` | `true` | MoveIt 起不起 RViz |
| `gate_timeout` | `180` | 等控制器 active 的总超时（秒） |

常用组合：

```bash
ros2 launch arm_bringup bringup.launch.py gui:=false         # 无界面，跑得快
ros2 launch arm_bringup bringup.launch.py use_moveit:=false  # 只要仿真 + 控制器
ros2 launch arm_bringup bringup.launch.py use_rviz:=false    # 要 move_group 但不要 RViz
```

#### 为什么中间要夹一个「门闩」节点

仿真那路的三个 spawner 是在 `gz_launch.py` 里用 `OnProcessExit` 一层层串的，
而且那是**被 include 进来**的动作——外层 launch 的 `OnProcessExit` 挂不到它
（`target_action` 只认本文件里定义的动作）。

也**不能**用固定延时（`TimerAction(period=30)`）：本机 RTF 只有 0.39，
30 s 真实时间只等于约 12 s 仿真时间，机器一忙就不够、空一点又白等。

所以用 `arm_bringup/scripts/wait_for_controllers.py` 去**问状态**：
它轮询 `/controller_manager/list_controllers`，直到
`joint_state_broadcaster` / `arm_controller` / `gripper_controller` 全部
`state == 'active'` 就退出，外层 launch 用 `OnProcessExit` 接住再拉起 MoveIt。
等多久取决于真的好了没有，不靠猜。

> 门闩超时（退出码 1）时 `bringup.launch.py` **照样**会启动 MoveIt。
> 这是故意的——MoveIt 起得来、用户能在日志里看到那条超时报错再去查 Gazebo，
> 好过整条链路静默不动。

#### 启动日志应该长这样

实测（`gui:=false camera:=false use_rviz:=false`，已裁剪）：

```
[INFO] [launch.user]: 机器人已生成，开始加载 joint_state_broadcaster
[ign gazebo-2] [INFO] [gz_ros2_control]: System Successfully configured!
[spawner-6] [INFO] [spawner_joint_state_broadcaster]: Configured and activated joint_state_broadcaster
[INFO] [launch.user]: joint_state_broadcaster 就绪，开始加载两个轨迹控制器
[spawner-7] [INFO] [spawner_arm_controller]: Configured and activated arm_controller
[spawner-8] [INFO] [spawner_gripper_controller]: Configured and activated gripper_controller
[wait_for_controllers.py-5] [INFO] [wait_for_controllers]: 控制器已全部 active：joint_state_broadcaster、arm_controller、gripper_controller
[INFO] [launch.user]: 控制器已就绪 → 启动 move_group 与 RViz
[move_group-9] [INFO] [moveit_robot_model.robot_model]: Loading robot model 'o5_2_arm'...

```

从敲下命令到 `You can start planning now!` 实测约 **15 s**（无界面、无相机）。

如果卡在「等待 `/controller_manager/list_controllers` 服务出现…」，
那是 **Gazebo 没起来**（世界文件 / 网格 / `gz_ros2_control` 插件的问题）——
去查 5.3 的启动链，**不要**在这里加大 `gate_timeout` 掩盖问题。

### 5.5 手动发指令

```bash
# 机械臂轨迹（用 action，不要用 topic pub —— 单条消息会被丢）
ros2 action send_goal /arm_controller/follow_joint_trajectory \
  control_msgs/action/FollowJointTrajectory \
  "{trajectory: {joint_names: [top_plate_joint, lower_arm_joint, upper_arm_joint, wrist_joint, claw_base_joint],
                 points: [{positions: [0.2, -0.2, 0.15, -0.1, 0.2], time_from_start: {sec: 5}}]}}"

# 夹爪：0 = 张开，负值 = 闭合
ros2 action send_goal /gripper_controller/gripper_cmd \
  control_msgs/action/GripperCommand "{command: {position: -0.35, max_effort: 20.0}}"
```

### 5.5b 抓取流水线（MTC 版，推荐）

`moveit_grasps` 在 ROS 2 上没有（仓库无 ros2 分支、apt 三个发行版都没有），
ROS 2 上的对应物是 **MoveIt Task Constructor（MTC）**。本工程已用它跑通：

```bash
ros2 launch arm_bringup bringup.launch.py gui:=false use_rviz:=false   # 仿真+MoveIt
ros2 launch arm_bringup grasp_mtc.launch.py                            # 只规划
ros2 launch arm_bringup grasp_mtc.launch.py execute:=true              # 规划并执行
ros2 launch arm_bringup grasp_mtc.launch.py probe:=true                # 打印候选抓取位姿
ros2 launch arm_bringup grasp_mtc.launch.py display:=true              # 发到 RViz 的 MTC 面板
ros2 launch arm_bringup grasp_mtc.launch.py place:=false               # 只抓不起（调试用）
ros2 launch arm_bringup grasp_mtc.launch.py perceive:=false            # 不用感知（调试用）
```

阶段链（`src/arm_bringup/scripts/grasp_pipeline_mtc.py`）：

    ① 摆到扫描位形（SRDF grasp_ready）
    ② 感知：腕部 RGBD 点云 → 剔地面 → 体素聚类 → 目标中心
    ③ 把感知到的物体放进规划场景
    ── 以下是 MTC 任务 ──
    CurrentState → Connect(到预抓取) → GenerateGraspPose(候选) →
    SimpleGrasp(IK + 闭爪) → 允许手指与方块接触 → 附着 → 抬起 →
    ── 以下是放回段（place:=true，默认开）── →
    搬到放置点上方 → 下压 → 张开 → 恢复碰撞检查 → 摘手 → 撤离

**② 为什么要单独摆到扫描位形**：腕部相机装在爪上，零位时光轴近乎水平
（实测与竖直夹角 85.2°），地面上的东西根本不在视野里。`grasp_ready` 位形
实测光轴偏竖直 12.3°、距目标 106 mm。感知脚本自己不动，它只负责"看"。

**感知精度**（对照 Gazebo 真值，2026-10-03 实测，臂在扫描位形）：

| | 均值 | 最差 |
|---|---|---|
| 中心 x | −1.1 mm | 1.1 mm |
| 中心 y | +0.6 mm | 0.8 mm |
| 中心 z | **+0.4 ~ +0.6 mm**（贴地反推，见踩坑记录第 40 条） |

抓取点抬高量 `GRASP_TCP_Z - 中心 z` 是**现算**的，不是常量 —— 位姿一改，
派生量必须跟着变，那种错误的症状是抓取点整体偏移几毫米、伺服报容差失败，
看不出根因。

**感知有有效性检查，失败会明确中止**：目标偏出相机视野时视野里只剩它一块
碎片，在碎片上算出来的中心能偏 **10 mm**，而这种错位**不报错**。所以结果
出来后校验「实测跨度 ∈ [0.8, 1.8] × 工件尺寸」，不合格直接退出（码 8），
流水线随之中止且**不碰方块**。详见 `docs/踩坑记录.md` 第 42 条。

> **自己的两指也在视野里**（两指之间净空 29.3 mm），在桌面上投出两条

> `tools/map_workspace.py`（下方）。

## 六、关键设计决策与理由

### 6.1 夹爪用「旋转对称」而不是平移

两指都是 `revolute`，绕同一根轴（`0 1 0`），限位镜像（`[−0.9,0]` / `[0,+0.9]`），
从动指用 `<mimic>` ×(−1)，控制器只驱主动指。

理由（手册批次 C 的实测结论）：**平移副在机械臂倾斜时会失效**——
Gazebo 的位置驱动增益被硬编码且改不了，平移关节的运动方向一旦与重力不平行，
重力就沿运动方向产生持续阻力，推不动。旋转副把重力变成「绕轴力矩」，
量级小得多；两指反向运动，重力矩还能互相抵消。

### 6.2 位置容差刻意保持严格

`arm_controller.constraints` 里 `trajectory: 0.05 / goal: 0.02 rad`。

实测可达姿态的跟踪残差是 **0.0000 rad**，所以这个容差不是"卡得紧"，
而是**同时充当"撞到东西"的探测器**——姿态撞地/撞物时 JTC 会以
`path tolerance violation` 报 ABORTED，而不是默默拖着走。

### 6.3 `arm_core.xacro` 自包含

参数、link、joint 全在一个文件里，不含任何 `$(find ...)` 外部 include，
也不含一行 Gazebo / ros2_control 内容。所以它可以**单独**展开验证：

```bash
xacro src/arm_description/urdf/arm_core.xacro > /tmp/a.urdf && check_urdf /tmp/a.urdf
```

### 6.4 为什么需要 `arm_gazebo/launch/gz_launch.py` 里的环境变量

Fortress 不认 `package://`，会把它当 `model://` 去资源路径里找目录。
不设 `IGN_GAZEBO_RESOURCE_PATH` / `GZ_SIM_RESOURCE_PATH` 的后果**非常隐蔽**：
网格全部静默失败——**视觉和碰撞体一起丢**，物理形同虚设，而控制器、接口、话题全是绿的。
判据：日志里 `grep -c "Unable to find file"` 必须为 **0**。
