## 零、先记住这套排查顺序

东西不对时不要乱试，按这个顺序走（每一步都便宜）：

1. **先看日志文件**，别看终端最后几行。`~/.ros/log/<时间戳>/launch.log` 才是全文。
2. **问"最底层的那个东西"**。ROS 层全绿不代表仿真对——直接问 Gazebo：
   `ign model -m <名字> -p`（位姿）、`ign topic -e /gazebo/<world>/world_stats`（是否暂停）。
3. **数数**。`grep -c "Unable to find file"`、`grep -c "<command_interface"`。
   计数为 0 或对不上，比"看起来没问题"可靠得多。
4. **单个隔离验证**。整条链不对时，把可疑环节单独拎出来跑（例：逐个关节单独发目标）。
5. **怀疑自己的符号约定**，再怀疑工具。见第 6 条——这是本次最大的一次弯路。

## 1. 同名 `robot_state_publisher` 抢走 `robot_description`

**症状**（Gazebo Classic 阶段）：

```
[ERROR] [gazebo_ros2_control]: parser error Couldn't parse parameter override rule:
  '--param robot_description:=<?xml version="1.0" ?> ...
   autogenerated by xacro from
   ~/ros2_arm/install/ros2_arm_description/share/ros2_arm_description/urdf/ros2_arm_gz.urdf.xacro
```

**根因**：`gazebo_ros2_control` / `gz_ros2_control` 是**按节点名** `robot_state_publisher`
去取 `robot_description` 的。当时机器上有一个 **41 分钟前残留的**
`ros2 launch ros2_arm_moveit_config demo.launch.py`（半死状态：spawner 卡死、没有 RViz），
它占着同名节点。插件连到了**旧的那个**，拿到的是 `ros2_arm` 的 URDF。

**判据**：报错里那段 URDF 的 xacro 路径**不是你自己的包**。看到就清残留进程，
不要去改自己的 URDF。

**修法**：清理残留。同一时刻只跑一个会注册 `robot_state_publisher` 的进程。

**连带发现**：`ros2 node list` / `ros2 service list` 会因 daemon 缓存出现**幽灵节点**——
列得出来，但实际调用超时：

```
$ ros2 control list_controllers
[INFO] waiting for service /controller_manager/list_controllers to become available...
[WARN] Could not contact service /controller_manager/list_controllers
```

判断服务是否真的活着**必须实际调用**，不要信 `ros2 service list`。
清理完执行 `ros2 daemon stop` 重置缓存。

## 2. 【Gazebo Classic】启动后停在暂停态，时钟不走

**症状**：控制器全 `active`、接口全 `claimed`，但
`ros2 topic hz /joint_states` 空转超时；而 `ros2 topic echo --once`
**却能返回一条消息，时间戳永远不变**。`/clock` 也读不到新值。

**根因**：世界处于 `paused: true`。

**判据**（注意话题前缀是**真实世界名**，不是 `default`）：

```bash
gz topic -l | grep world_stats
gz topic -e /gazebo/arm_empty/world_stats -d 2 2>&1 | grep -E 'paused|iterations'
#   paused: true      ← 就是它
#   iterations: 0
```

**修法**：启动时加 `-r`（立即运行），或临时
`ros2 service call /unpause_physics std_srvs/srv/Empty`。

**本工程现状**：`gz_launch.py` 里已写死 `gz_args: ['-r -v4 ', world]`。

## 3. 【Gazebo Fortress】网格全部静默加载失败（视觉与碰撞一起丢）

**症状**：日志里每个网格一条错，但没有任何"致命"字样：

```
[Err] [SystemPaths.cc:379] Unable to find file with URI [model://arm_description/meshes/claw_base.stl]
[Err] [MeshManager.cc:173] Unable to find file[...]
[Err] [Ogre2MeshFactory.cc:562] Cannot load null mesh [...]
[Err] [SceneManager.cc:404] Failed to load geometry for visual: link5_visual
```

**根因**：URDF 里写的是 `package://<包>/meshes/x.stl`，**gz sim 不认 `package://`**，
它按 `model://` 去**资源路径**里找名叫 `<包>` 的目录。没设环境变量就找不到。

**为什么这条最危险**：丢的不只是视觉——**碰撞体是同一批网格，一起丢了**。
模型看着像一副空骨架，物理却形同虚设（穿模、没有接触）。
而控制器状态、硬件接口、话题全都是绿的，你根本不会怀疑这里。

**判据**：

```bash
grep -c "Unable to find file" <启动日志>     # 必须为 0
```

**修法**（写在 launch 里，且必须排在起 Gazebo 的 action **之前**——
`SetEnvironmentVariable` 只对之后启动的进程生效）：

```python
from launch.actions import SetEnvironmentVariable
share_parent = os.path.join(get_package_share_directory('<包>'), os.pardir)   # <install>/share
SetEnvironmentVariable(name='IGN_GAZEBO_RESOURCE_PATH', value=share_parent),
SetEnvironmentVariable(name='GZ_SIM_RESOURCE_PATH',     value=share_parent),
```

两个变量名都设：Fortress 认 `IGN_GAZEBO_RESOURCE_PATH`，新一点的 gz 认 `GZ_SIM_RESOURCE_PATH`。

## 4. mimic 关节在接口清单与 `/joint_states` 里名字变成 `<原名>_mimic`

**症状**：

```
$ ros2 control list_hardware_interfaces
	left_claw_joint_mimic/position [available] [unclaimed]

$ ros2 topic echo /joint_states --once --field name
['top_plate_joint', ..., 'right_claw_joint', 'left_claw_joint_mimic']
```

**这不是故障，不要"修"**：

- `[unclaimed]` 是对的——mimic 关节由联动关系驱动，本来就不该被控制器占用；
- `/joint_states` 里带 `_mimic` 后缀也**不会**让 TF 断掉——
  `robot_state_publisher` 自己会按 URDF 的 `<mimic>` 算出从动关节的值。

**验收方法**：发一个主动关节指令，看两关节是否**严格反向等量**（和 ≈ 0）：

```
指令 -0.6 -> jaw_a=-0.6000  jaw_b=+0.6000  和=-0.000000
```

## 5. `ABORTED due to path tolerance violation` —— 先怀疑几何，再怀疑驱动

**症状**：

```
[ERROR] [arm_controller]: Holding position due to state tolerance violation
error_string: Aborted due to path tolerance violation
Goal finished with status: ABORTED
```

最容易被误判成"驱动太弱 / 增益不够"。**判别实验很快，务必做**：

> 把 5 个关节**逐个单独**发目标（其余保持在 0），看残差。

本次实测结果：

```
top_plate_joint  目标=+0.600 实测=+0.6000 残差=0.0000 rad
lower_arm_joint  目标=-0.500 实测=-0.5000 残差=0.0000 rad
upper_arm_joint  目标=+0.400 实测=+0.4000 残差=0.0000 rad
wrist_joint  目标=-0.300 实测=-0.3000 残差=0.0000 rad
claw_base_joint  目标=+0.500 实测=+0.5000 残差=0.0000 rad
```

**每个单独都能精确到位 ⇒ 驱动与容差都没问题，去查几何。**

**根因确认**：拿展开后的 URDF 对目标关节角做一次正运动学，算各 link 与夹爪的 **z 值**：

```
B 大幅 [0.6,-0.5,0.4,-0.3,0.5]:  right_claw z = -0.0356 m   ← 地面在 z=0
A 小幅 [0.2,-0.2,0.15,-0.1,0.2]: right_claw z = +0.0812 m   ← 通过
```

夹爪钻到地面以下 3.6 cm → 顶住 → 连基座回转（top_plate_joint）都被接触摩擦卡住，
这解释了"绕竖直轴的关节居然也走不到"这个反直觉现象。

**结论**：这是**正确的物理**，不是链路故障。

**修法**：换可达姿态，或把模型抬高。
**不要放宽容差**——严格容差（0.05/0.02 rad）反而成了很好的"碰撞探测器"。

## 6. 最大的一次弯路：抓取几何的符号搞反了

**经过**：设计抓取时，我用 FK 扫关节空间找"两指竖直朝下"的构型，
得到"**腕部永远在抓取点下方 95.8 mm**"的结论，于是推导出：

> 抓取点正下方 78 mm 被腕部占满 → 托住方块的台面只能挤在 15.2 mm 的夹缝里
> → 而且这条臂**够不到自己所在的安装面**（俯抓时 TCP 最低 0.237 m）

我据此设计了一个"悬臂薄托板 + 立柱"的世界文件，还写进了注释。
**全都是错的。**

**根因**：手指相对腕部的位置由 jaw 关节原点偏移决定：

```
jaw = claw_base − 0.0824 × plate_long        (plate_long = jaw 局部 +Z)
```

- `plate_long` 指向 **+Z（朝上）** → jaw 在腕**下方** → 手指挂在腕下 = **正常俯抓姿态**
- `plate_long` 指向 **−Z（朝下）** → jaw 在腕**上方** → 腕在手指下方 = 反的那一支

我扫的是后者。两支结论完全相反：

| | 朝下（错的那支） | 朝上（正确） |
|---|---|---|
| TCP z 可达范围 | [0.237, 0.444] | **[−0.167, 0.039]** |
| 腕相对抓取点 | 下方 95.8 mm | **上方 95.8 mm** |
| 能否够到地面 | 够不到 | 够得到 |

**判据（很便宜，务必先算）**：正常"从上方俯抓"的位形里，
**腕关节必须在抓取点上方**，手指挂在腕的下方。
如果算出来是反的，**先怀疑自己的符号约定**，别急着下"这个臂做不到"的结论，
更别据此去设计支撑结构。

**教训**：遇到"几何上不可能"的结论时，先做一个同量级的对照检查
（这里是"腕在上还是在下"），再往下走。

## 7. 控制器热重载 YAML 不可靠，别信 `Successfully switched controllers`

**场景**：想改 `constraints` 又不想重启仿真，于是：

```bash
ros2 control switch_controllers --deactivate arm_controller
ros2 control unload_controller arm_controller
# 改 yaml（--symlink-install 下立刻生效）
ros2 control load_controller arm_controller
ros2 control switch_controllers --activate arm_controller   # 打印 "Successfully switched controllers"
```

**实测后果**：命令说成功，但

```
$ ros2 control list_controllers
arm_controller   joint_trajectory_controller/JointTrajectoryController   unconfigured

$ ros2 action send_goal ...
Waiting for an action server to become available...
Failed to check if action server is available
```

**修法**：改 `constraints` 这类配置变更**直接重启仿真**（几十秒），
不要在这条路上省时间。真要热重载，用
`ros2 control set_controller_state <c> active` 并**立刻用 `list_controllers` 回读确认**，
不要只看 CLI 的复述。

## 8. `ign gazebo` 是 ruby wrapper，清理要看进程树

**进程树**：

```
/bin/sh -c ruby /usr/bin/ign gazebo ...
  └─ ign gazebo ...
       ├─ ign gazebo server
       └─ ign gazebo gui
```

**修法**：先 `ps` 拿 PID 再 `kill`；`gui`/`server` 常忽略 SIGTERM，补 `kill -9`：

```bash
ps -eo pid,args | grep -E 'ign gazeb[o]' | grep -v grep
```

**一个隐蔽的自杀方式**：不要在**同一条命令**里既 `pkill -f 'ign gazebo'`
又 `pgrep -af 'ign gazebo'`——后者让 pkill 命中当前 shell 自己，
整条命令被 SIGTERM 打断，后半段（含清理动作）根本没执行。
症状：退出码 143、输出为空、进程其实还在。pattern 用字符类 `'ign gazeb[o]'` 可以避免。

## 9. 本机没有 `ign_ros2_control` 这个包

**背景**：手册里写"`ign_ros2_control` 和 `gz_ros2_control` 是同一个东西的两个名字，
两个都写上最保险"。

**实测**：

```bash
$ ls /opt/ros/humble/share/ | grep -iE 'ign_ros2_control|gz_ros2_control'
gz_ros2_control                      # 只有这个
```

**影响**：
- `package.xml` 里**只声明 `gz_ros2_control`**（写 `ign_ros2_control` 会是个悬空依赖）；
- 但插件名**两种都能用**——`gz_ros2_control` 内部保留了兼容别名：
  ```bash
  $ cat /opt/ros/humble/share/gz_ros2_control/gz_hardware_plugins.xml
  name="gz_ros2_control/GazeboSimSystem"          ← 推荐
  name="ign_ros2_control/IgnitionSystem"          ← 向后兼容别名
  ```
- 系统插件：`filename="gz_ros2_control-system"`
  `name="gz_ros2_control::GazeboSimROS2ControlPlugin"`（实测 `.so` 里注册的就是这个符号）。

**教训**：手册的结论要**在本机复核一遍再用**，不要照抄。

## 10. 可动物体必须有 `<inertial>`，否则"怎么抓都提不动"

**症状**：方块明明被夹住了，抬起动作也 `SUCCEEDED`，但方块纹丝不动。

**根因**：SDF 里的 `<model>` 如果没写 `<inertial>`，Gazebo 会警告并按**静态**处理。
静态物体不受力、不移动——摩擦抓取对它完全无效。

**修法**：给质量与惯量（25 mm、20 g 的方块）：

```xml
<inertial>
  <mass>0.020</mass>
  <inertia>
    <ixx>2.083e-06</ixx><ixy>0</ixy><ixz>0</ixz>
    <iyy>2.083e-06</iyy><iyz>0</iyz>
    <izz>2.083e-06</izz>
  </inertia>
</inertial>
```

同时**去掉 `<static>true</static>`**。

## 11. `GripperActionController` 返回 `stalled: true, reached_goal: false` 是正常的

**症状**：

```
Result:
    position: -0.35...
    stalled: true
    reached_goal: false
```

**为什么正常**：夹爪的闭合量**故意给得比物体尺寸大**。
夹爪开口 29.28 mm、方块 25 mm：
- `−0.15 rad` 才刚碰到方块；
- 给到 `−0.35 rad` 才能**压紧**——靠位置误差产生接触力，摩擦才抓得住。

被方块挡住 → 到不了目标 → `stalled: true`。**判定时不要把它当失败**。

**判据**：真验收要看**方块有没有被提起来**（读 Gazebo 位姿），不是看这个返回值。

## 14. PATH 被高版本 Python 污染，colcon 会挂

**症状**：

```
ModuleNotFoundError: No module named 'catkin_pkg'
CMake Error at .../ament_package_xml.cmake:95 (message):
  execute_process(/usr/local/bin/python3.13 ...)
```

**根因**：PATH 里 Python 3.13 排在前面，而 `catkin_pkg` 只装在 3.10。

**修法**：

```bash
env -i HOME=$HOME PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
  bash -c "source /opt/ros/humble/setup.bash && cd ~/arm5_ws && colcon build --symlink-install"
```

**隐藏坑**：如果之前用"脏 PATH"编译过一次，`build/<包名>/CMakeCache.txt` 里会
**缓存住错误的 Python 路径**，之后即使 PATH 干净了也照样报错，表现为"一个包一个包地失败"。
这时要单独删掉：

```bash
rm ~/arm5_ws/build/*/CMakeCache.txt
```

## 15. MoveIt：`.setup_assistant` 是隐藏文件，CMake 默认不会装它

**症状**：move_group 起来了，但模型是空的，日志里一串：

```
WARNING:root:Cannot infer URDF from `/.../arm_moveit_config`. -- using config/o5_2_arm.urdf
WARNING:root:Cannot infer SRDF from `/.../arm_moveit_config`. -- using config/o5_2_arm.srdf
WARNING:root:"File .../config/o5_2_arm.urdf doesn't exist"
WARNING:root:The robot description will be loaded from /robot_description topic
```

**根因**：`moveit_configs_utils` 靠包根目录下的 **`.setup_assistant`** 推断
URDF 在哪个包、哪个相对路径。而 CMake 的

```cmake
install(DIRECTORY config launch DESTINATION share/${PROJECT_NAME})
```

**只搬 config 与 launch，根目录的隐藏文件不搬**。装到 `install/` 里就没有它了。

**修法**：单独写一条 install 规则：

```cmake
install(FILES .setup_assistant DESTINATION share/${PROJECT_NAME})
```

**判据**：`ls -la install/<包>/share/<包>/.setup_assistant` 必须存在。

## 16. MoveIt：`pilz_cartesian_limits.yaml` 不存在会让 launch 直接崩

**症状**：

```
[ERROR] [launch]: Caught exception in launch (see debug for traceback):
  "File .../config/pilz_cartesian_limits.yaml doesn't exist"
```

**根因**：`MoveItConfigsBuilder.to_moveit_configs()` 默认会读这个文件，**读不到就抛异常**，
整个 launch 起不来。本工程根本不用 Pilz 规划器，但文件仍然必须在。

**修法**：建一个文件。**但不要留空字典**——留空虽然能起来，move_group 会刷 4 条 ERROR：

```
Parameter 'robot_description_planning.cartesian_limits.max_trans_vel', is not set in the config file.
（max_trans_acc / max_trans_dec / max_rot_vel 同理）
```

按 Pilz 官方默认值填上即可（`max_trans_vel: 1.0` / `max_trans_acc: 2.25` /
`max_trans_dec: -5.0` / `max_rot_vel: 1.57`）。

## 17. 5 自由度臂接 MoveIt：不设 `position_only_ik` ，IK 永远解不出来

**症状**：RViz 里拖目标位姿，点 Plan 一直失败；`/compute_ik` 返回 `error_code = -1`。
日志里**没有**任何有用的解释。

**根因**：本臂只有 5 个自由度（top_plate_joint..claw_base_joint）。KDL 默认做**完整 6D 位姿** IK，
6 个约束 5 个未知量 —— 数学上无解，不是"调参能调出来"的。

**修法**：在 `kinematics.yaml` 里对每个规划组加一行：

```yaml
arm:
  kinematics_solver: kdl_kinematics_plugin/KDLKinematicsPlugin
  position_only_ik: true          # ← 关键
```

开启后 KDL 只用位置（3 个约束）求解，姿态自由度由它自行分配。
对取放、抓取这类任务足够用。

**验证**：

```bash
ros2 service call /compute_ik moveit_msgs/srv/GetPositionIK \
"{ik_request: {group_name: arm, ik_link_name: tcp, timeout: {sec: 2},
  pose_stamped: {header: {frame_id: world},
    pose: {position: {x: 0.0267, y: 0.12, z: 0.20}, orientation: {w: 1.0}}}}}"
#   成功 → error_code val=1
#   失败 → error_code val=-1
```

本机只装了 KDL（没有 pick_ik / trac_ik / bio_ik），所以只能走这条路。
参数名可用 `strings libmoveit_kdl_kinematics_plugin.so | grep position_only` 确认。

## 18. MoveIt 的碰撞矩阵不能省：相邻连杆对必须显式禁用

**症状**：move_group 起来后任何规划都失败，说起点或路径在碰撞；
或者 `/compute_ik` 即使 `avoid_collisions: false` 也怪怪的。

**根因**：MoveIt **默认检查所有连杆对**，包括用关节直接相连的相邻对。
而本模型的**腕部相机碰撞盒（7×24×20 mm）就套在 claw_base 原点附近**，
和 claw_base 的网格必然重叠 → 模型"天生就在自碰撞"。

**修法**：在 SRDF 里显式列出相邻对：

```xml
<disable_collisions top_plate="claw_base" lower_arm="wrist_cam_link" reason="Adjacent"/>
<disable_collisions top_plate="claw_base" lower_arm="right_claw" reason="Adjacent"/>
...
```

**只禁用相邻对和确定不碰的对**；其余非相邻对**保持检查** ——
那是我们要的（让规划器避开真正的自碰撞姿态）。

Setup Assistant 会自动采样生成这张表；手写的话至少要保证相邻对齐全。

## 19. 别用 `generate_demo_launch()`，它会再起一个 `ros2_control_node`

**背景**：`moveit_configs_utils.launches.generate_demo_launch()` 看着很方便，
一行就能起 MoveIt + RViz。

**问题**：它还会起 **`ros2_control_node` + 一串 controller spawner**。
而本项目的控制器是 `gz_ros2_control` 插件**在 Gazebo 进程内**提供的——
再起一个外部 controller_manager 就是两个 manager 抢同一批关节，
表现为 spawner 报 `Failed loading controller`、控制器状态错乱。

**修法**：手写 launch，只起 `move_group` 与 RViz：

```python
from moveit_configs_utils import MoveItConfigsBuilder
moveit_config = MoveItConfigsBuilder("o5_2_arm", package_name="arm_moveit_config").to_moveit_configs()

Node(package="moveit_ros_move_group", executable="move_group",
     parameters=[moveit_config.to_dict(), {"use_sim_time": True}])
```

同理：**不要**再起第二个 `robot_state_publisher`（仿真那边已有，同名会互相抢，
见第 1 条）。

## 20. MoveGroup action 的 `start_state` 不在 `planning_options` 里

**症状**：

```
Failed to populate message fields:
AttributeError("'PlanningOptions' object has no attribute 'start_state'")
```

**根因**：写错了层级。`start_state` 属于 **`MoveGroupRequest`**（即 `request`），
`planning_options` 里只有 `plan_onl`/`plan_only`、`look_around`、`planning_scene_diff` 等。

**正确写法**：

```
{request: {group_name: arm, ..., start_state: {is_diff: true},
           goal_constraints: [...]},
 planning_options: {plan_only: false}}
```

`start_state: {is_diff: true}` 表示"以当前状态为起点"，规划时**必须**带上，
否则 MoveIt 会去读 SRDF 里的默认状态。

## 22. JTC 的 `path tolerance` 卡住了速度上限 —— 但那个滞后不是故障

**现象**：把 MoveIt 的速度缩放到 0.25 以上，`/move_action` 就回
`CONTROL_FAILED(-4)`，move_group 日志里真正的错是：

```
[WARN] Controller 'arm_controller' failed with error PATH_TOLERANCE_VIOLATED:
       Aborted due to path tolerance violation
[INFO] Solution found but controller failed during execution
```

**别急着放宽容差**，先测清楚滞后是多少。JTC 的 `~/state` 话题里带
`error` 字段（= reference − feedback），直接用它：

```bash
ros2 topic echo /arm_controller/state --field error
```

实测（MoveIt 速度缩放 = s，本机 3 ms 物理步长）：

| s | 峰值跟踪误差 | 移动耗时 | 结果（容差 0.05 时） |
|---|---|---|---|
| 0.15 | 0.0300 rad | 15.3 s | 通过 |
| 0.20 | 0.0400 rad | 12.9 s | 通过 |
| 0.25 | 0.0500 rad | 11.4 s | 失败，顶到容差 |
| 0.30 | 0.0499 rad | 6.8 s | 失败 |

**误差 ≈ 0.20 × s，严格线性。** 这不是故障，是 `gz_ros2_control` 位置接口
背后那套**软位置伺服**跟动参考时留下的恒定滞后 —— 速度翻倍，滞后翻倍。

**结论与做法**：`trajectory` 容差从 0.05 放到 **0.12 rad（6.9°）**，
`goal` 容差**保持 0.02 不变**（终点精度不能松）。然后选缩放 0.40：

| s | 峰值误差 | 对 0.12 容差的余量 | 移动耗时 |
|---|---|---|---|
| 0.30 | 0.060 | 50% | 8.4 s |
| **0.40** | **0.080** | **33%** | **6.9 s** |
| 0.50 | 0.100 | 17% | 6.0 s |
| 0.60 | 0.120 | 0% | 被掐断 |

注意：0.12 rad 仍然是有效的故障网：真撞上东西偏差会远超 0.12 rad。

注意：顺带纠正一条**旧结论**：本文第 5 条曾写"严格容差是撞东西的保护，别放宽"。
那句话在"容差是唯一故障判据"时成立；接入 MoveIt 之后规划期有 OMPL 的碰撞检查、
执行期有 Gazebo 自己的接触解算，JTC 容差退化成第三道网，**该按被控对象的
真实能力来定**，而不是越紧越好。

## 23. 实时因子（RTF）的瓶颈是**物理步长**，不是相机

**先看错的方向**：以为软件渲染下相机拖慢了仿真，把 `arm_camera.xacro` 从
640x480@30Hz 降到 320x240@10Hz —— 像素吞吐降了 9 倍，**RTF 一点没变**（0.139）。

**取证**：20 核的机器，负载才 5~6，CPU 根本没吃满；但
`ign gazebo server` 稳定占 **107% ≈ 1 个核** —— 单线程物理被填满的特征。

**真正有效的**：`worlds/arm_world.sdf` 里

```xml
<physics name="3ms" type="ignored">
  <max_step_size>0.003</max_step_size>     <!-- 原来是 0.001 -->
  <real_time_factor>1.0</real_time_factor>
</physics>
```

| | 1 ms | 3 ms |
|---|---|---|
| RTF | 0.139 | **0.391** |
| 一个抓取流程 | ~4 分钟 | **59.7 s** |

**2.8 倍**，而且没有精度代价（`real_time_factor` 是上限不是保证值）。

注意：步长放大会让接触解算变"硬"，**会反过来影响夹爪抓取效果**（见第 27 条）。

## 25. 抓到的物体必须从世界**摘下来**，否则抬起时 fraction = 0

**现象**：下压、闭合都正常，紧接着的竖直抬起 `compute_cartesian_path`
返回 `fraction = 0.000`、只解出 1 个点 —— 一条路都走不了。

**判决实验**（同一段竖直抬升，只改一个参数）：

```
avoid_collisions=True   →  fraction=0.000   点数=1
avoid_collisions=False  →  fraction=1.000   点数=22
```

⇒ **是碰撞检测卡的，不是 IK。**

**根因**：抓取的本质就是**手指几何压进方块**。手指一闭合，方块还留在
世界坐标系里的话，MoveIt 就认为【机器人当前状态就在碰撞】，
于是路径第一步就判无效。

**做法**：用 MoveIt 的惯例把物体**挂到手上**，并声明哪些连杆允许与它接触：

```python
aco = AttachedCollisionObject()
aco.link_name = 'claw_base'                                    # 挂到哪
aco.touch_links = ['claw_base', 'tcp', 'right_claw', 'left_claw']  # 谁可以碰它
aco.object.id = 'target_cube'
aco.object.operation = CollisionObject.ADD                 # ← 操作码在 object 上
scene.robot_state.attached_collision_objects = [aco]
```

注意：`touch_links` 里**必须包含手指**，否则挂上了手指与方块照样算碰撞。

注意：松手时别忘了摘下来+按实测位姿重新登记回世界，否则世界模型与实际不符。

## 26. 复位方块用了"瞬移"，而臂正夹着它 → 报错点离根因十万八千里

**现象**：重跑演示时第一步"回零位"直接 `CONTROL_FAILED(-4)`，
日志还是一样的 `path tolerance violation`。查了半天速度、容差、规划场景，
都不是。

**根因**：`ign service ... /world/<world>/set_pose` 是**瞬移**。上一次演示
中途失败，方块正好被夹在手指里；瞬移把它直接塞进手指的碰撞体，
接触解算爆出巨大冲击把整条臂弹开，关节跟不上参考 → JTC 掐断。

**做法**：开局先"清场"——把方块扔到臂够不着的地方（本工程用 `(0.55, 0.55, 0.05)`，
地面 20x20 m 兜得住），**再**回零位，然后**才**复位方块。这一步让演示能从
任何烂摊子里自我恢复、反复跑。

**另一类卡死**：臂被**地面**顶住。实测残留姿态下 `right_claw` 的网格
最低点 z = **−0.0146 m**（手指插进地 1.5 cm），这时候回零位的轨迹能规划出来、
但关节根本推不动。**没有便宜的解法，重启仿真最省事**；演示里"回零位"这一步
改用低速（scale 0.2）可以磨出轻度卡滞。

## 27. 夹爪闭合角要按几何算 —— 多压 6.9 mm 会把方块**挤跑**

**现象**：夹爪报 `stalled=True` 且 `position` 停在 0.0000（手指像没动）；
有时方块被提起来、有时提不起来，**不稳定**。

**根因**：闭合指令给得太深。在本工程的抓取位形下，
两指夹持面间距随 `jaw_a` 角的变化是：

| jaw_a 角 | 面间距 | 对 25 mm 方块的压入量 |
|---|---|---|
| 0.00 | 29.28 mm | −4.28 mm（还没碰到） |
| **−0.1465** | **25.00 mm** | **0（刚好贴住）** |
| −0.20 | 23.29 mm | +1.71 mm |
| −0.35（原值） | 17.77 mm | **+6.87 mm** |

方块是刚体，压不进去。命令多压 6.9 mm 的后果是物理引擎**把它往外挤** ——
实测夹爪一闭合方块就被推走 **11 mm**（y: 0.0245 → 0.0352），
于是"夹爪闭上了但方块没被抓住"。

注意：**这个坑是被第 23 条（物理步长 1 ms → 3 ms）放大的**：步长大，接触解算更硬，
同一个闭合角从"偶尔失败"变成"经常失败"。**改物理参数后一定要重跑抓取验收。**

**修法**：`GRIP_CLOSE` 从 −0.35 改成 **−0.20**（只留 ~1.7 mm 余量）。
接触刚度 `kp = 1e6 N/m`，0.1 mm 就是 ~100 N 量级，根本不需要压那么深。

**通用教训**：这类"指令超出接触位置"的量，**都该用几何算，不该手调**——
本工程的几何表由 `tools/grasp_geometry.py` 现场算，改方块尺寸后重算即可。

## 28. 后台进程与 Python 缓冲

- **`nohup ... &` / `... &` 起的进程会随启动它的 shell 退出被清理。**
  长驻进程（Gazebo、MoveIt）必须用**后台任务机制**起，不要自己加 `&`。
- 把脚本输出重定向到文件时，Python 是**块缓冲**的 —— 日志要等进程结束才刷出来，
  中途 `cat` 是空的，会误判成"卡住了"。加 `python3 -u`。
- **别在同一个命令里既 `pkill -f 'xxx'` 又 grep 'xxx'**：
  `pkill -f` 会匹配到自己的命令行，把自己这个 shell 杀掉（SIGTERM）。

## 29. 批量重命名 link/joint 时，把 SRDF 的 **`link1=` / `link2=` 属性名**也改了

**背景**：把模型从 `link1..link5 / joint1..joint5` 改成语义命名
（`top_plate / lower_arm / upper_arm / wrist / claw_base`）时，用正则批量替换
`\blink1\b → top_plate`、`\blink5\b → claw_base` 扫全工程。

**问题**：SRDF 的碰撞矩阵里，**属性名本身就叫 `link1` 和 `link2`**：

```xml
<disable_collisions link1="link2" link2="link3" reason="Adjacent"/>
```

于是替换后变成：

```xml
<disable_collisions top_plate="lower_arm" lower_arm="upper_arm" reason="Adjacent"/>
```

值改对了，**属性名改错了** —— MoveIt 读不到 `link1`/`link2`，
整张碰撞矩阵等于**一条都没生效**。

**症状**（很能骗人，因为报错完全不提 SRDF）：

```
[moveit_collision_detection_fcl] Found a contact between 'lower_arm' and 'upper_arm',
                                 which constitutes a collision.
[moveit_ros.fix_start_state_collision] Start state appears to be in collision with respect to group arm
[WARN] Unable to find a valid state nearby the start state ...
[ompl] Skipping invalid start state (invalid state)
[ERROR] arm/arm: Motion planning start tree could not be initialized!
→ /move_action 返回 FAILURE(99999)，轨迹 0 点
```

**读法**：`lower_arm` 与 `upper_arm` 是**由关节直接相连的相邻连杆**，
它们"碰撞"在几何上是不可能的 —— 这一定不是真的干涉，而是
**相邻对被漏掉了**，要回头查 SRDF。

**修法**：只改属性**值**，不改属性**名**：

```python
for ln in lines:
    if '<disable_collisions' in ln:
        ln = ln.replace(' top_plate=', ' link1=').replace(' lower_arm=', ' link2=')
```

**通用教训**：批量改名前先 `grep` 一遍属性名，别只想着"值"。
同一个词在 XML 里既可能是标签名、也可能是属性名、还可能是值：

```bash
grep -rn 'link1\|link2' src/          # 改之前先看它都出现在什么位置
grep -rnE '<[a-z_]+ (新名)=' src/     # 改之后再扫一遍"新名出现在属性名位置"
```

改完**必须**重新验一遍完整链路（不能只看 xacro 能展开）：
漏掉 SRDF 这一处，`check_urdf`、控制器、`list_hardware_interfaces` **全是绿的**，
只有真正调用 `/move_action` 才会暴露。

## 30. 放回时按 TCP 回到"原抓取高度"会把方块顶进地面

**现象**：抓、抬都正常，最后一步"下压放回"报

```
[WARN] Controller 'arm_controller' failed with error GOAL_TOLERANCE_VIOLATED:
       Aborted due to goal_time_tolerance exceeding by 1.003995 seconds
```

注意**错误类型变了**：不再是 `PATH_TOLERANCE_VIOLATED`（途中超差），
而是 `GOAL_TOLERANCE_VIOLATED`（**终点收敛不了**）。这两个要分清楚：
前者是跟不快，后者是根本到不了。

**根因**：抓起时命令 TCP 到 `grasp_z = 0.0231`（由指尖离地间隙推出来的）。
放回时如果**照抄同一个高度**，就忽略了方块的姿态：

| | 方块中心 z | 姿态 | 沿世界 Z 的支撑半长 | 最低点 |
|---|---|---|---|---|
| 放回前实测 | 0.1464 | rpy = (**0.743**, −0.092, 0.058) | **18.74 mm** | 0.1277 |
| 平放时 | — | rpy = 0 | 12.50 mm | — |

方块被夹着抬起时会带**几十度的倾角**（本次实测 42°），
于是它沿竖直方向的支撑半长从 12.5 mm 涨到 18.7 mm。
命令 TCP 回到原高度，等于把方块**往地面里按 2.9 mm** ——
方块是刚体按不进去，伺服就永远收敛不了，JTC 只能以 goal_time 超时收场。

实测：TCP 停在 0.0260，差目标 2.9 mm 死活下不去，同时方块最低点算出来
**正好是 0.0000**（贴地）。

**修法**：**别命令 TCP 到某个绝对高度，而是命令"方块最低点到某个高度"**。
用支撑函数（support function）把姿态算进去：

```python
# 立方体半边长 h，姿态旋转矩阵第三行 r ⇒ 沿 ±Z 的最大伸出
support = h * (|r_zx| + |r_zy| + |r_zz|)
# 想让方块最低点停在离地 clearance：
drop = (cube_z - support) - clearance
tcp_target = tcp_now - drop
```

本工程取 `clearance = 8 mm`，剩下的 8 mm 让方块自己落下去
（20 g 的方块落 8 mm，对最终落点的影响在毫米级；实测放回误差 Δx = −0.23 mm）。

**通用教训**：凡是"命令某个绝对高度"的地方，都要问一句
**"这个高度是相对谁的？"**。抓取里所有跟位姿有关的量，
要么按几何算、要么按实测算，别跨阶段照抄常数 ——
抓起阶段的常数，到放回阶段前提条件已经变了。

## 31. `CONTROL_FAILED(-4)`：一度以为 `wrist_joint` 被锁死，干净环境下根本没复现

**现象**：抓取演示到最后的「回零位」这一步：

```
[9] MoveIt 规划回零位
      规划耗时 0.00 s   轨迹 28 点   总耗时 1.1 s   错误码 -4
    失败（错误码 -4）
```

规划**是成功的**（有 28 点轨迹），死在执行上。move_group 只说：

```
[WARN] Controller 'arm_controller' failed with error PATH_TOLERANCE_VIOLATED
[WARN] Completed trajectory execution with status ABORTED ...
[INFO] Solution found but controller failed during execution
```

**报错点离根因很远**：`PATH_TOLERANCE_VIOLATED` 只说明控制器被掐断了，
不说为什么。真正的信息在 **Gazebo 那一侧的日志**里（不是 ROS 侧）：

```
[ign gazebo-2] [ERROR] [tolerances]: State tolerances failed for joint 3:
[ign gazebo-2] [ERROR] [tolerances]: Position Error: 0.124762, Position Tolerance: 0.120000
[ign gazebo-2] [WARN] [arm_controller]: Aborted due to state tolerance violation
```

### 为什么"joint 3 到底是谁"必须查清楚

日志里写的是 **`joint 3`（索引），不是关节名**。控制器的关节表是

```
索引:   0              1               2               3          4
名字:   top_plate_joint lower_arm_joint upper_arm_joint wrist_joint claw_base_joint
```

所以 `joint 3` = **`wrist_joint`**。而 `/joint_states` 里的顺序是
`top_plate, upper_arm, lower_arm, wrist, ...`（URDF 顺序）——
**两处顺序不同**。按 `/joint_states` 的顺序数会数成 `claw_base_joint`，
一路查错方向。

判据（两条独立确认）：
- 先看数据（下节的采样器），误差最大的关节是 `wrist_joint`，
  峰值 0.117，而其余四个 ≤ 0.011 —— **差一个数量级**。
- 再看 move_group 的另一句日志：`Starting state is just outside bounds
  (joint 'wrist_joint')` —— 它点名的也是腕关节。

### 用 `tools/jtc_trace.py` 一眼看出真因

```bash
python3 tools/jtc_trace.py /tmp/jtc.csv 60     # 另开终端发目标
```

它采 `/arm_controller/state`（`JointTrajectoryControllerState`）——
`error` 字段是**控制器自己算的** `reference − feedback`，
比拿 `/joint_states` 自己重建参考轨迹可靠得多。

实测那段（`act` 来自 `/joint_states`）：

```
     wrist_act   wrist_err   wrist_ref      ← 参考 = act + err
      -1.57080     0.00001    -1.57079
      -1.57080     0.01905    -1.55175
      -1.57080     0.04704    -1.52376
      -1.57080     0.09543    -1.47537
      -1.57080     0.12138    -1.44942     ← 越过 0.12，掐断
```

**`wrist_act` 一动不动**，参考值以约 0.1~0.24 rad/s 正常推进。
所以误差是**单调线性上涨**的，不是抖动。判据一句话：

> 误差是"线性累积"→ 关节没动；误差是"有界波动"→ 关节在跟但跟不上。

### 关键教训：报错里的 0.12 是**容差本身**，不是测量结果

第一次跑和第二次跑分别读到 `Position Error: 0.124762` 和 `0.121382`，
都≈0.12。当时的理解是"两种速度下误差一样 → 与速度无关"。
**这个理解是错的**：容差就是 0.12，报错值必然是
"第一个超过 0.12 的采样"，**它只告诉你越线了，不告诉你为什么**。
不要拿报错值当被测量用。

### 排除掉的原因（都是实测，别重复走）

| 猜想 | 结论 | 证据 |
|---|---|---|
| 速度太快、伺服跟不动 | 已排除 | 0.40 与 0.20 两档**都在同一处失败** |
| 腕关节坏了 | 已排除 | 从零位走到 -1.5708 再回 -1.45，`SUCCEEDED` |
| ABORT 之后控制器死锁 | 已排除 | 故意制造违规后再发同样的慢速移动，`SUCCEEDED` |
| 是那个姿态本身 | 已排除 | 拿当时那组关节角原样重放，`SUCCEEDED` |
| 被地面/工件顶住 | 已排除 | 失败时 TCP 在 **z = 0.124 m** 的空中 |

### 我原来写在这里的解释，是错的

原来这一段写的是"腕关节压在 -1.5708 上进入锁存状态，容差守卫把误差钳在
0.12 rad，于是伺服永远只能拿到小误差 → 小速度命令，冲不出这个顶死的位置"。
把第 32 条的双仿真清干净、在**干净的单仿真**上重做之后，这个解释站不住：

| 我试过的 | 结果 |
|---|---|
| 从零位走到 -1.5708 再回 -1.45 | `SUCCEEDED` |
| 拿失败时那组关节角原样重放 | `SUCCEEDED` |
| 故意制造容差违规，紧接着发良性移动 | `SUCCEEDED` |
| 干净单仿真跑整条演示，连做三轮 | **一次都没复现**，控制器零条容差告警 |

而第 32 条已经证明：那两次失败发生时，机器上**同时有两个 `ign gazebo server`
在跑**，`/arm_controller/state` **有两个发布者**。当时的采样器没有过滤发布者，
于是"参考值正常推进、实际值一动不动、误差线性累积"这套看上去很干净的证据，
本身就可能只是**两份仿真的消息交替拼出来的**。

所以这一条的正确结论是：

> 报错是真的（控制器确实把那条轨迹掐断了），
> 但"腕关节物理上不动"这个证据不可信。
> 在干净的单仿真上，这条臂跑完整演示从来没有真正 ABORT 过。

### 真实情况：误差峰值一直是容差的 2/3

干净单仿真上逐关节实测（基线那一轮）：

| 关节 | 硬限位 | 实际最靠近限位 | 误差峰值 | 占 0.12 容差 |
|---|---|---|---|---|
| top_plate | ±1.5708 | -0.007 | 0.004 | 3% |
| lower_arm | ±1.5708 | -0.249 | 0.050 | 42% |
| upper_arm | ±1.5708 | -0.389 | 0.034 | 28% |
| wrist | ±1.5708 | **-1.57080（就是限位本身）** | 0.077 | 64% |
| claw_base | ±1.5708 | **-1.57080（就是限位本身）** | 0.080 | 67% |

两件事值得记下来：

1. 腕部的**两个**关节都**确实被规划到了硬限位正上方**（实测 -1.5708000110，
   比限位多 1e-8）。原因不是它俩特殊，而是 `position_only_ik` 下
   KDL 会随手把自由度多的关节推到变量边界上停住——**这是 IK 的解算习惯，
   不是物理现象**。
2. 误差和"离限位多近"**不成正比**：`lower_arm` 离限位 1.3 rad 远，
   误差照样有 0.050。真正把误差顶上去的是**这个关节在轨迹里走得多不多**。

### 处置：给腕部两个关节加位置余量（已做）

`arm_moveit_config/config/joint_limits.yaml` 给 `wrist_joint` 和
`claw_base_joint` 各加了 0.0708 rad 的位置余量（±1.5708 → ±1.50）。
三轮实测对照：

| 指标 | 加余量前 | 只收 wrist | 两个都收 |
|---|---|---|---|
| wrist 实际最小 | -1.57080 | -1.42448 | -1.13087 |
| claw_base 实际最小 | -1.57080 | -1.56261 | -0.00177 |
| wrist 误差峰值 | 0.077 | 0.065 | 0.080 |
| claw_base 误差峰值 | 0.080 | 0.080 | 0.013 |
| lower_arm 误差峰值 | 0.050 | 0.050 | 0.073 |
| 提起高度 | 130.5 mm | 133.0 mm | 132.6 mm |
| 放回误差 Δx | +13.63 mm | -0.17 mm | -2.45 mm |
| 收尾回零位 | 成功 | 成功 | 成功 |
| 控制器容差告警 | 0 条 | 0 条 | 0 条 |

**必须说清楚：余量并没有把误差峰值压下去。** 它只是把误差从"压在硬限位上的
关节"挪到了"走得最多的关节"上（`claw_base` 0.080 → 0.013，代价是
`lower_arm` 0.050 → 0.073）。三轮里最坏的那个数一直是 0.08 上下，
也就是容差的 2/3。

所以这层余量的定位是**工程正确性**，不是"治好了那个报错"：
规划器不应该产出正好落在硬止点上的目标，命名预设也不应该越过自己的
规划边界。它**不构成** `CONTROL_FAILED` 的根因修复。

另一个副作用值得记：只收 wrist 那一轮，方块放回误差从 +13.63 mm 降到
-0.17 mm；两个都收是 -2.45 mm。这是**单次**结果，还不能断言是余量的功劳
（落点本来就受夹持姿态和释放时刻影响），但至少说明收紧余量没有把抓放搞坏。

### 顺带修掉的一个真问题：SRDF 预设越过了新的规划边界

`o5_2_arm.srdf` 里的 `grasp_ready` 原来写的是 `wrist_joint = -1.55`。
加上 ±1.50 的余量之后它直接越界，拿它当起始状态会报

```
Starting state is just outside bounds (joint 'wrist_joint')
```

已经把它收到 -1.45。但注意 **`tools/pick_demo.py` 的 `PREGRASP` / `LIFT`
还写着 -1.55**（离硬限位只有 0.021 rad），那条路径不走 MoveIt、没有位置余量
约束，所以暂时不受影响；如果以后要给那条路径也加余量，得把这两个数一起重解
并重跑验证。

### 一句话判据

容差违规排查里，"某关节一动不动"这个证据**只有在确认全机只有一个仿真在跑时
才可信**（第 32 条）。先证环境唯一，再看关节。

## 32. 清理不干净 → 两个仿真同时在跑 → 一整批测量全是假的

**这是本次最贵的一个坑**：`pkill` 的模式没匹配上，我以为清干净了，
其实两个 `ign gazebo server` 并行跑了几分钟，期间读到的每一个
"实测值"都不可信。

**为什么没匹配上**：`ros2 launch` 拉起来的 Gazebo，命令行是

```
/bin/sh -c ruby /usr/bin/ign gazebo -r -v4 <world>.sdf -s --force-version 6
                ign gazebo -r -v4 <world>.sdf -s
```

**没有 "server" 这个词**（`-s` 才是 headless 的意思）。
而 `pkill -f 'ign gazebo serve[r]'` 找的是字面量 `ign gazebo server` ——
一个都匹配不到。（早先那个孤儿进程的 `argv` 恰好是 `ign gazebo server`，
所以那次能杀掉，给了"这个模式有效"的错觉。）

**另一个自杀陷阱**：`pkill -f 'move_group'` 会命中**我自己这条 shell**
（命令行里就含 `move_group` 这个词）。实测结果就是工具直接返回
`Signal: SIGTERM`，而且**链在后面还没执行的 pkill 全都没跑**——
于是第一个仿真活了下来。

**怎么发现的**：

```bash
ps -eo pid,cmd | grep -E 'arm_worl[d]\.sdf' | grep -v grep | wc -l   # 应为 1，实测 2
ros2 topic hz /clock        # 应为 ~150 Hz，实测 ~310 Hz（两份时钟叠加）
```

**造成过哪些错误结论**（写下来，因为它们当时看起来非常像真的）：

- 读到关节初始位置是 `[0.002, -0.304, 0.479, -1.5708, 0.094]`，
  于是判断"这台臂一上电就重力垮到折叠姿态、腕关节倒在限位上"。
  **假的。** 单仿真干净启动时实测是 `[0, 0.0003, -0.0001, -4e-10, 0, 0]`——
  全零，而且控制器能稳住。之前那个姿态只是**上一次 ABORT 留下的残姿**。
- 那一轮 demo 的 `[0] 回零位` 报 -4，看起来"全新仿真也失败"。
  实际是 `/joint_states` 被两份发布者搞乱，
  move_group 报 `Didn't receive robot state (joint angles) with recent
  timestamp within 1.000000 seconds` / `Failed to validate trajectory`——
  **完全不是同一个故障**。
- 采样文件 0 字节、`err` 全 0，当时都当成"实验设计问题"，
  其实是话题已经乱了。

**正确的清理方式**（按命令行特征，不按进程名；模式里加字符类避免自匹配）：

```bash
ps -eo pid,cmd | grep -E 'arm_worl[d]\.sdf|moveit_ros_move_grou[p]|ros_gz_bridg[e]|robot_state_publishe[r]' \
  | awk '{print $1}' | xargs -r kill
# 然后必须数一遍：
ps -eo pid,cmd | grep -E 'arm_worl[d]\.sdf' | grep -v grep | wc -l   # 必须 = 1
```

**通用教训**：**任何"实测"之前，先证明实验环境是唯一的。**
这条比本次任何一个技术细节都重要 —— 环境被污染时，测量不会报错，
它会**安静地给你一个看起来合理的错误答案**。
判据很便宜：数进程数 + 看 `/clock` 频率是不是单份。

## 33. MTC 的规划器拿不到参数 → 轨迹时间戳**全是 0**，执行必挂

**现象**：`ros2 launch arm_bringup grasp_mtc.launch.py execute:=true` 规划一路成功
（有解、代价正常、阶段树也对），但执行时机械臂一步不动：

    [move_group]    sending trajectory to arm_controller
    [move_group]    Goal request rejected / Goal was rejected by server
    [arm_controller] Time between points 0 and 1 is not strictly increasing,
                     it is 0.000000 and 0.000000 respectively
    [move_group]    Failed to send trajectory part 1 of 1 to controller arm_controller

**根因**：rclcpp 默认 `automatically_declare_parameters_from_overrides = False`。
launch 传进来的参数是**覆盖项**，没被"声明"就 `node->has_parameter(...)` 返回 false。
而 MTC 建 `PlanningPipeline` 时正是用 `has_parameter` 去查适配器列表：

    // moveit_ros planning_pipeline.cpp
    if (node_->has_parameter(parameter_namespace + "." + adapter_plugins_param_name))
        node_->get_parameter(..., adapters);      // 查不到 → 适配器列表为空

适配器一空，**MoveIt 的时间参数化就不做了**（`AddTimeOptimalParameterization`
本身就是个请求适配器），于是规划出来的轨迹每个点 `time_from_start` 都是 0。
规划阶段完全看不出来，只在执行时炸。

**注意**：MTC 自己会对 `ompl.planning_plugin` 显式 `declare_parameter`，所以规划器
类型能查到（日志会打印 `Using planning interface 'OMPL'`）——**这条日志不能证明
适配器也加载了**。真正的判据是下面这几行：

    正常：Using planning request adapter 'Add Time Optimal Parameterization'
          ...（共 6 条 adapter）
    异常：只有 Using planning interface 'OMPL'，一条 adapter 都不打印

**修法**（`arm_bringup/scripts/grasp_pipeline_mtc.py`）：

    opts = rclcpp.NodeOptions()
    opts.automatically_declare_parameters_from_overrides = True
    node = rclcpp.Node('grasp_pipeline_mtc', opts)

## 34. MTC 的抓取点在**物体中心**，会让指尖戳进台面

**现象**：执行到"接近"这一段就被掐断，报的不是碰撞而是容差：

    [tolerances] State tolerances failed for joint 2:
                 Position Error: 0.027348, Position Tolerance: 0.020000
    [arm_controller] Aborted due to goal_time_tolerance exceeding by 1.008657 seconds

**降速治不了它**：把笛卡尔段缩放从 1.0 降到 0.25，误差 0.0269 → 0.0273，
几乎不变 —— 说明是**静态偏差**，不是跟踪滞后。别在这上面绕。

**根因**：`GenerateGraspPose` 生成的位姿，原点就在**物体中心**（probe 模式实测
25 个候选位置全是 (0,0,0)，即物体参考系原点）。可是 `tcp` 是两指夹持面中点，
指盒沿指长方向有 ±18.5 mm。把 tcp 放到方块中心（离台面 12.5 mm）的结果是：

    tcp       = (0.0267, 0.0245, 0.0125)      ← 正好在方块中心
    right_claw 碰撞盒 z ∈ [-0.0054, +0.0304]  ← 负值就是戳进台面 5.4 mm

物理上顶住桌面，伺服永远收敛不了。

**修法**：抓取点必须**高于**物体中心，沿用 `tools/pick_demo_moveit.py` 已标定的
`GRASP_TCP_Z`（= 台面 + 指尖间隙 0.0046 + 指盒半长 0.0185 = 0.0231 m）。
在 MTC 里就是给 `ik_frame` 加一个 z 偏移：

    ik.pose.position.z = GRASP_TCP_Z - 物体中心高度    # 本工程 = 0.0106

核校（用 `tools/grasp_geometry.py` 的 FK 一算就出来）：tcp 落在 0.0231，
指尖离台面 +5.5 mm，两指 x 区间仍分列方块两侧。

## 35. 夹爪关节完全不动：控制器必须**重新申领**一次命令接口

**现象**：最难查的一个。`/joint_states` 里 `right_claw_joint` 恒为 **0.000000**，
怎么发指令都不动。而控制器那一侧**完全正常**：

    ros2 action send_goal /gripper_controller/gripper_cmd ... → SUCCEEDED
    （stalled: true, reached_goal: false，但状态是 SUCCEEDED）

而且它**欺骗性极强**：让轨迹控制器去一个**远超限位**的目标（+0.5，限位 [-0.9, 0]），
它照样回 `Goal successfully reached!` —— 说明它读到的"位置"根本不是物理状态。

**根因**：gz_ros2_control 只在【控制器申领接口】时，才在 `perform_command_mode_switch`
里把关节的 `joint_control_method` 置成 POSITION。仿真刚起那一轮，夹爪控制器的
申领**没有生效**，于是关节落进"没设控制方式"的分支：

    else if (joints_[i].is_actuated) {   // 兜底：给一个 0 速度指令
        target_vel = 0.0;                // → 关节被按在原地
    }

**修法**：全部控制器 active 之后，把夹爪控制器停掉重起一次：

    ros2 control set_controller_state gripper_controller inactive
    ros2 control set_controller_state gripper_controller active

已经做进 `arm_bringup/scripts/wait_for_controllers.py`（`--reactivate` 参数），
`bringup.launch.py` 默认会对 `gripper_controller` 做这一步，不用手动。

**连带的设计改动**：`GripperActionController` **不能**用在这个修复上 —— 它在
`on_init()` 里就把命令句柄缓存下来了，重新申领之后写的是**失效的旧句柄**，
命令写了、关节还是不动。而 `JointTrajectoryController` 每次 `on_activate`
都重新绑定接口，活得下来。所以夹爪控制器改成了 JTC。

改 JTC 的代价是：到不了目标位置就会报 `GOAL_TOLERANCE_VIOLATED`，而
"夹住方块后手指停住"恰恰是到不了。所以闭合角必须按几何给到**刚好压住**的量：

    SRDF 预设姿态 close: -0.20 → **-0.15**（压入量约 0.14 mm）

`-0.20` 在 GripperActionController 时代是对的（它把"停住"判成成功），
换成 JTC 之后必须跟着改，否则闭合那一段会被判失败。

## 36. 放回段用 GeneratePlacePose + ComputeIK 会报接口方向不匹配

**现象**：按 MTC 官方 demo 的拓扑接放回段（`lower object` → `GeneratePlacePose`
+ `ComputeIK` → `open hand` → `forbid collision` → `detach object` → `retreat`），
装进 `SerialContainer` 后直接初始化失败：

    place pose IK: interface of 'generate place pose' (← →) does not match
                   external one (→ →).
    open gripper: cannot initialize to unknown interface
    forbid object collision: cannot initialize to unknown interface
    ...
    o5_2 pick and place: end interface (?) of 'place object' does not match mine (→)

**根因**：`GeneratePlacePose` 是**反向(←)接口**的生成器（它靠 monitored stage
喂状态），而包它的 `ComputeIK` 继承自 `WrapperBase` → `ParallelContainerBase`，
接口检查是**严格相等**的（`ParallelContainerBasePrivate::validateInterfaces`
里 `valid = (external & mask) == (child_interface & mask)`）。串行容器在
非首位给子阶段派发的期望接口与它对不上，就抛这个异常。

注意报错信息很有误导性：最后一行说的是「'place object' 的 end interface
不匹配」，看起来像放置目标不可达；真正的错在**上一行**。

**修法**：改用 `MoveTo` + `PoseStamped` 目标指定 tcp 位姿，整条放回链于是
全是正向(→ →)阶段，可以像 pick 链那样直接挂在 task 上。顺带一个好处：
官方那套里 `ComputeIK` **只改状态、不产生轨迹**，机械臂并不会真的动到 IK 解；
换成 `MoveTo` 之后每一段都有真实轨迹。

> 官方 demo 能这么写是因为它整条 `place` 容器是从 `Connect` 之后接的，
> `Connect` 是双向的，能桥接 (→) 到 (←)。本工程的放回链是接在 `lift`
> （正向阶段）后面的，没有那个桥。

**顺带**：MTC 的 Python 绑定**没有**暴露 `children()`，所以没法遍历容器打印
阶段树或按名查子阶段。`report_failures()` 因此只能按阶段名列表查
（`task['阶段名']`），且 `SimpleGrasp` 容器里的子阶段要单独列出来。

## 37. `MoveTo` 给 PoseStamped 目标时，必须配笛卡尔求解器

**现象**：放回段第一段 `MoveTo('move to place', PipelinePlanner(node))` 配 OMPL
规划器，13 条输入全军覆没：

    [ompl] ./src/ompl/geometric/planners/rrt/src/RRTConnect.cpp:265 -
           arm/arm: Unable to sample any valid states for goal tree
    [moveit.ompl_planning.model_based_planning_context]: Invalid goal state
    Failing stage(s): move to place (0/13): GOAL_STATE_INVALID

看起来像"放置位姿不可达"。**不是。**

**根因**：`MoveTo::compute()` 按 goal 的类型分两条路（见 `move_to.cpp`）：

    if (getJointStateGoal(...))       // 关节空间目标
        planner_->plan(state.scene(), scene, jmg, timeout, traj, constraints);
    else                              // 笛卡尔目标（PoseStamped / PointStamped）
        planner_->plan(state.scene(), *link, offset, target, jmg, ...);

`PoseStamped` 走的是**笛卡尔分支**，调的那个重载只有 `CartesianPath` 实现得了。
喂 `PipelinePlanner`（OMPL）进去不会报"接口不对"，只会一路走到 OMPL 然后炸在上面。

**修法**：`MoveTo('move to place', cartesian)` —— 复用 `approach`/`lift` 那一套
降速笛卡尔求解器（`CART_VEL_SCALE = 0.25`）。

**判据**：别用 `/compute_ik` 去验笛卡尔目标。笛卡尔分支**压根不做 IK**，
`/compute_ik` 返回成功只说明位置可达，说明不了这一段能规划出来。

## 38. OMPL 规划器名写错，两轮都没人发现

**现象**：日志里一直有这条告警，从上一轮就在：

    Cannot find planning configuration for group 'arm' using planner
    'RRTConnectkConfigDefault'. Will use defaults instead.

而代码注释里恰好写着断言，说这个名字**不能**写成 `RRTConnect`，理由就是
上面那句告警——结论正好反了。

**根因**：MoveIt 2 humble 的 `PlanningContextManager` 认的是
`ompl_planning.yaml` 里 `planner_configs` 列表中的**原名**，不会自动加
`kConfigDefault` 后缀。所以 `RRTConnectkConfigDefault` 查不到，
规划器退回 OMPL 的裸默认参数（`geometric::RRTConnect`）。

危害等级：规划**照常成功**，只是解变差 —— 又一处"安静地给错答案"。

**修法**：`pipeline.planner = 'RRTConnect'`。实测代价从 **6.53 降到 3.89**。

**判据**：日志里出现 `Will use defaults instead` 就是名字写错了；
正常时打印的是 `Planner configuration 'arm[RRTConnect]' will use planner
'geometric::RRTConnect'`。

## 39. kinematics.yaml 给非 chain 的组配 IK 求解器，每次启动刷三条 ERROR

**现象**：加载机器人模型时刷三条 ERROR：

    Group 'gripper' is not a chain
    Kinematics solver of type 'kdl_kinematics_plugin/KDLKinematicsPlugin'
      could not be initialized for group 'gripper'
    Kinematics solver could not be instantiated for joint group gripper

**根因**：`gripper` 组是两个**独立**的指关节（`right_claw_joint` 与作为
`<mimic>` 从动的 `left_claw_joint`），没有共同末端，不是 chain，KDL 直接拒绝。

**修法**：把 kinematics.yaml 里 gripper 那一段删掉。它从来没被用到 ——
夹爪开合一律走 `JointInterpolationPlanner`（1 个自由度，插值就是精确解），
不需要 IK。留着只会让人以为夹爪也走 IK。

> 改完 ERROR 消失，但**要重启 move_group 才见效**（长驻节点不会重读 yaml）。

## 40. 顶面高度取 `max`，让感知系统性地高估物体中心 2 mm

**现象**：把感知接进抓取流水线后，抓取时**方块会被手指推着走** —— 实测
闭合那一步 x 被推了 1.3 mm。抓是抓起来了，但这个"推"是设计之外的力。

**根因**：链条是这样的 ——

    中心 z 偏高  →  抓取点相对物体偏低  →  手指多压 1.4 mm  →  把方块推开

而中心 z 是这么算的：相机近乎垂直向下（光轴偏竖直 12.3°），只能看到物体
**顶面**，于是靠"平顶物体贴地放置"反推：

    center_z = (z_ground + z_top) / 2

`z_top` 原本取的是该簇的 `max`。**这是错的**：相机不 在正上方，同一个水平
顶面在点云里是**斜的** —— 远边的 z 比近边高。取 `max` 等于专门去用"远边
那条棱"，而那条棱离相机最远、深度噪声最大。

实测：25 mm 的方块，`max` 给出离地 **27.7 mm**（偏高 2.7 mm）。

**为什么这个误差特别要命**：第 27 条记着实测多压 1.7 mm 就能把方块挤走
11 mm。感知给的 2.7 mm 已经超过那个量级 —— 一个"看起来只有几毫米"的算法
误差，落在机械上就是"把工件推走"。

**修法**：改取 **90 分位**。它落在顶面那片区域里，又避开了最外圈那条棱和
长尾噪声。之所以敢用分位数，是因为这一簇是**平面分割 + 连通域**的结果，
主体就是顶面本身，不是侧面或杂散点；分位取得太低才会切进顶面内部。

| | `max` | 90 分位 |
|---|---|---|
| 顶面离地高度 | 27.7 mm（真值 25） | **25.8 mm** |
| 中心 z 误差 | +1.4 mm | **+0.3 ~ 0.6 mm** |
| 抓取时被推 | 1.3 mm | **0.9 mm** |
| 实测抬起量 | 36.2 mm | **40.2 mm** |

**顺带一个更隐蔽的错**：脚本 `--model` 的真值对照里，`dz` 原本是拿
`center[2]`（点云包围盒中心）去比物体中心真值。这一簇基本就是顶面，
`center[2] ≈ 0.026`（顶面高度），拿它比 `0.0125` 会凭空报出 **+12 mm**
的误差 —— 看着像算法彻底坏了，其实只是比错了对象。能比的只有贴地反推出来的
`center_z`。这种"诊断信息本身是错的"比没有诊断更糟，会把人引向完全错误的
方向。

## 41. 点云量出的工件尺寸系统性偏大约 15%，不能直接当碰撞盒用

**现象**：`estimate_object_pose.py --json` 输出的 `size_xy` 在
**26.5 ~ 28.2 × 29.2 ~ 31.4 mm** 之间跳，而真值是 25 × 25 mm。

**根因**：量的是**顶面在点云里的投影范围**，叠上三样东西：边缘外扩、深度
噪声（std 约 1.3 mm）、以及倾斜视角把顶面拉长。波动大是因为分割出的点数
本身不稳定（实测 1300 ~ 2600 点）。

**处理**：流水线的碰撞盒尺寸**不取感知值**，用配置项 `OBJECT_SIZE`。
理由不只是"数值不准"——工件尺寸本来就不是现场才知道的东西，它来自图纸/BOM，
属于配置。要用感知尺寸，得先把那份系统膨胀标定掉（固定相机参数下标一张
"实际尺寸 ↔ 观测尺寸"的对照表）。

判断一个量能不能直接用，先问它**是不是只有感知才拿得到**。尺寸不是。
